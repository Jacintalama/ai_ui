# Local Docker first, then agent animations in step with what agents do (design)

Date: 2026-10-12. Status: approved the same day.

## Why

1. **Smooth, accurate animation.** The request: agents' animations during
   chats, collaborations and meetings should be smooth and in step with what
   the agents are actually doing, and the office should feel connected,
   realistic and polished.
2. **No staging site.** Today every change is tried on the live site. The
   request: test locally in Docker first, then promote to live accurately.

## What was found (2026-10-12)

1. **The office learns about agents only from five events on
   `/agents/stream`:** `run_started`, `tool_started`, `tool_finished`,
   `handoff` and `run_finished` (`office/js/office.js` `applyEvent`).
   - Each event redraws the whole floor (`draw()`).
   - Nothing marks the moment an agent's reply appears in the chat, so a
     robot cannot speak in step with the answer.
   - A meeting is inferred from run sources; nothing marks the turn order.
2. **The animation code is Ralph's** (`static/office.html`,
   `static/office/**`). He commits to it almost daily; the latest are 10-08
   and 10-09.
3. **Docker Desktop 29.7.2 with Compose 5.5.1 is installed** on the dev
   machine (32 GB RAM, 16 threads), currently stopped. A stale
   `docker-compose.local.yml` (April) exists as an override of the
   30-service production compose.

## Decisions

1. **Ownership.** We build the shared event layer, the local stack and the
   agents-page side. Office files change only where needed, in small commits
   rebased on Ralph's latest, and Ralph is told before they land.
2. **Local model.** A scripted fake model is the default (free and
   repeatable). A switch selects a real OpenRouter key: free models only,
   paid escalation off (`AGENT_PAID_DAILY_CAP=0`).
3. **Surfaces.** The full robot animation lives in the Agent Office page,
   which has its own chat since 10-09. The agents list and the thread show
   the same moments in miniature.
4. **Sync approach.** One shared server timeline. Rejected:
   - client-side guessing, which only works when chat and office share a
     page, never for Discord, Slack or a second tab;
   - a game-engine rewrite, which is too big and replaces Ralph's office.

## Part 1: local Docker

1. **`docker-compose.dev.yml`**, standalone (not an override of production),
   with six services: `postgres`, `tasks`, `open-webui`, `api-gateway`,
   `caddy` and `fake-llm`. It serves `http://localhost:8090`.
2. **`.env.dev.example`** is committed. `.env.dev` is gitignored and holds
   dev-only secrets, generated by the setup script. The production `.env` is
   never copied, and no production data is used.
3. **Seed:** a local admin user and three agents (Mia, Ada, Dev), on the
   default model.
4. **`fake-llm`:** an OpenAI-compatible streaming endpoint that plays scripted
   scenes with fixed timings, chosen by keywords in the message:
   - single answer;
   - tool call;
   - handoff;
   - a three-agent meeting;
   - a failure.

   `LOCAL_MODEL=real` points it at OpenRouter instead.
5. **`scripts/dev_up.sh`** handles up, seed, health check and reset.
6. **Rule recorded in `CLAUDE.md`:** change locally, run the tests, check in a
   browser against local Docker, then deploy with the existing hash-checked
   method.
7. **Unknowns to settle in the plan, by reading code, not guessing:**
   - how agent turns reach a model (through Open WebUI or directly);
   - what Open WebUI needs on first boot;
   - what the gateway needs for local auth.

## Part 2: shared event layer (tasks)

1. **New events on the existing `/agents/stream`:**
   - `speaking_started` and `speaking_finished` (agent, conversation, turn);
   - `meeting_started` (participants in turn order);
   - `turn_started`;
   - `meeting_ended`.

   They are emitted from the chat round at the moment a bubble starts and
   ends. They fail open: a dropped event never breaks a chat.
2. **Measured in local Docker** with the fake model's fixed timings: the delay
   from the event to the visible robot change, before and after. The target
   is 200 ms or less.

## Part 3: office director (office files, small commits)

1. **A per-robot state machine:** idle, working, speaking, walking, meeting.
   - Each state has a minimum time on screen, so quick events do not
     flicker.
   - Moves are queued: a walk finishes before speaking starts, and a meeting
     gathers, takes turns, then disperses in order.
2. **Smooth motion:**
   - only transform and opacity are animated (Web Animations API), with
     ease-out timing;
   - no full-floor redraw on each event; only the robots that changed are
     touched;
   - `prefers-reduced-motion` gives instant state changes.
3. **Connected feel:**
   - the speaking robot's name is highlighted;
   - a soft line links the two agents in a handoff;
   - the meeting room is lit while in use;
   - the to-do panel and the activity feed update from the same events.

## Part 4: agents page in miniature

1. List avatars show a working pulse and a speaking ring.
2. The thread shows system lines, drawn only from real events:
   - "Dev asked Mia";
   - "Meeting: Mia, Ada, Dev".

## Testing

1. Browser tests for each scripted scene, run against local Docker, with
   timing asserted against event times.
2. Before and after screen recordings of each scene.
3. The existing suites stay green.
4. Nothing goes live until it passes locally.

## Order

Part 1, then Part 2, then Part 3, then Part 4. Each part is promoted to live
only after it passes locally.

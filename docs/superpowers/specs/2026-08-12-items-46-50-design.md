## 46 — the cap applies to Discord and Slack admins. Leave it.

`webhook-handler/clients/tasks.py` sends only `X-User-Email` — never
`X-User-Admin` — so an admin creating a schedule from Discord is capped like any
other user, while the same person is exempt on the web.

**This is not a bug to fix.** The tasks service trusts `X-User-Admin` *because*
the API gateway strips it from the client request and re-sets it only after
validating the JWT (verified live: a forged `X-User-Admin: true` gets 401). The
webhook-handler is not the gateway. If it started asserting admin-ness, the
header would become forgeable-by-proxy and the invariant that makes it
trustworthy anywhere would be gone.

An admin needing more than 10 schedules has the web UI (gateway-authenticated)
or the operator secret. Action: document the reasoning in the code so the next
person does not "fix" it.

### A correction this forced

An earlier review flagged `Caddyfile:238-242` — `/tasks/schedules*` routes
straight to `tasks:8210`, bypassing the gateway, and strips `X-User-Email` but
not `X-User-Admin`. I dismissed it as inert because CLAUDE.md says prod Caddy is
a host systemd service. **CLAUDE.md is wrong** (see below), so that block IS
live. Re-tested properly against production:

```
POST /tasks/schedules  no headers                  -> 403
POST /tasks/schedules  forged email + forged admin -> 403
```

Safe — the stripped `X-User-Email` makes `_resolve_caller` refuse before
`x_user_admin` is read, and a caller with the cron secret is an operator and
exempt anyway. The conclusion held; the reasoning behind it did not.

## 47 — `/run-now` has no limit

`routes_schedules.py:336` resolves the caller, scopes the schedule to its owner,
then fires `asyncio.create_task(_finalize_run(sched))` and returns
`{"status": "dispatched"}`. Nothing bounds how often. Each run spawns a Claude
Code agent; `_RUN_SEMAPHORE` caps concurrency at 3, so the box will not OOM, but
the queue grows without limit and genuine scheduled runs starve behind a burst.

**Fix:** refuse when a run for that schedule is already in flight — "it is
already running" is both the honest answer and the bound. With the 10-schedule
cap already in place, a user's worst case becomes 10 queued runs rather than
unbounded. Operators and admins keep today's behaviour.

## 48/49 — export, versions and docs for the people who own the app

"Take Your App With You" shipped 2026-07-27. It is admin-only, so the owners it
was built for cannot use it.

**These are NOT the redundant gates fixed on 2026-08-11.** Those endpoints
(`list_tasks`, `get_task`, `execute`) each enforced ownership in the body, so
the admin header was a second lock on a locked door. These do not:

```
list_versions   _require_role hits: 0
get_docs        _require_role hits: 0
export_bundle   _require_role hits: 0
export_guide    _require_role hits: 0
```

`export_bundle` validates the slug, takes the build lock, and zips. Swapping the
dependency alone would let **any signed-in user download any app's full source,
git history, and injected Supabase config**. The check has to be written first.

**Scope (Jacint's choice):** the four read-only endpoints above. `export` and
`export/guide` require `owner`; `versions` and `docs` require `viewer`, matching
`get_supabase`'s precedent that a pure read is viewer-level. The capability path
is unchanged.

**Explicitly out of scope:** `members`, `presence`, `leave`, and
`DELETE /{slug}`. They have no ownership check either, and `DELETE` is
destructive. They stay admin-only until each gets its own analysis.


## Testing

Everything except the config changes is ordinary Python with unit tests. The
security-critical assertions:

- a signed-in stranger cannot export, read docs, or list versions for an app

- an owner can; a viewer can read docs/versions but not export;
- the capability path still works and is never treated as admin;

  once finished.

`docker-compose.unified.yml` — the gap was config, not code, and the existing
tests could not see it because they set the value themselves.
